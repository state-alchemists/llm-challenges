# 2026-06-25

## Written ADR-001: Notification Architecture Decision

**Context:** Read `system_context.md` — a SaaS project management platform at 85k MAU, 500 req/s peak, with synchronous notification dispatch causing timeouts (800ms avg, 8s spikes), silent failures, and cascading outages.

**Task:** Evaluate Apache Kafka vs Redis Streams as an async event broker for the notification subsystem. Deliverable: a structured ADR.

**Research gathered via web:**
- [Redis Streams official retry + DLQ tutorial](https://redis.io/tutorials/redis-backed-job-queue-for-background-workers/) — confirms consumer groups, `XAUTOCLAIM` reclaim, dead-letter stream patterns
- [Confluent Kafka delivery semantics docs](https://docs.confluent.io/kafka/design/delivery-semantics.html) — confirms exactly-once operates within cluster boundary, requires app-level idempotency for external side effects
- Community comparison articles confirming Redis Streams as the pragmatic choice for moderate workloads with existing Redis infrastructure

**Decision:** Redis Streams. Key justification:
1. Zero new infrastructure (Redis already in production)
2. Team already knows Redis; no Kafka experience
3. Satisfies ≤2-week delivery constraint
4. Exactly-once for billing handled via application-layer idempotency keys in PostgreSQL — a pattern Kafka would also require for external API calls
5. Redis Pub/Sub provides the WebSocket push path on the same stack
6. ~1,500 events/s at current scale, ~15,000 at 10x — well within Redis throughput
